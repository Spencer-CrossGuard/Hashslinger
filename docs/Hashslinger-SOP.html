What it does

Reads account NT hashes from AD (read-only), looks each one up in a local store of breached and weak password hashes, and writes a CSV of the flagged accounts. Account hashes stay in memory and are wiped after the run. The only network traffic is to the domain controller. Nothing in the tool changes AD.

Folders

One folder you pick at setup. Everything lives inside it:

Hashslinger\
  app\            program and scripts (Hashslinger.exe, powershell\, config\ defaults, docs\)
  app-backups\    the last 3 copies of app\ taken before an upgrade or reinstall
  config\         hashslinger.json (the ONE settings file), pattern_rules.json, hashslinger.json.bak-* (save backups)
  data\store\     master.ntlm (merged hash store) + master.ntlm.manifest.json (which files are merged)
  data\staging\   HIBP\  rockyou\  custom\   (wordlist files)
  reports\        report_<date>.csv
  logs\           audit.jsonl, setup-*.log, SETUP-SUMMARY.txt
  status\         status.json (live progress), run.lock (one scan at a time)
  requests\       analyst request drop box (only if an analyst group is used)
  extras\         optional gMSA helper scripts
  Hashslinger-Admin.cmd   Hashslinger-Uninstall.cmd

Outside the folder: two scheduled tasks (Hashslinger-Scheduled, Hashslinger-OnDemand), the DSInternals module (%ProgramFiles%\WindowsPowerShell\Modules), the RSAT AD tools feature, support bundles you create (Desktop), and the service account in AD.

Install

  1. Create the service account first (next section).
  2. Copy the package to the scan server, double-click Setup-Hashslinger.cmd (local administrator).
  3. Pick the install folder, the DC, the service account name, and tick scope in the tree (ticking an OU includes everything below it; search keeps parents visible). Optional: rockyou and HIBP files, offline DSInternals folder.
  4. Check readiness (changes nothing), then Install. Install = local install, then the service account checks.

Setup phases (the wizard runs these; you can run them yourself): Setup-Hashslinger.cmd -Phase Check|Local|Finish|All -Config <folder>\config\hashslinger.json [-WhatIf]

Refuses to run while a scan is running.

Service account (created by hand)

The tool never creates or changes anything in AD. A Domain Admin creates the account once:

# KDS root key, once per forest (skip if Get-KdsRootKey returns one)
Add-KdsRootKey -EffectiveImmediately          # usable after ~10 hours, once every DC has it

# The account. Only the scan server may retrieve its password.
New-ADServiceAccount -Name svc-hashslinger `
  -DNSHostName svc-hashslinger.corp.contoso.com `
  -PrincipalsAllowedToRetrieveManagedPassword (Get-ADComputer SCANSERVER) `
  -KerberosEncryptionType AES256

# Two rights on the DOMAIN ROOT only, "this object only" (never forest, never schema):
#   Replicating Directory Changes       1131f6aa-9c07-11d1-f79f-00c04fc2dcd2
#   Replicating Directory Changes All   1131f6ad-9c07-11d1-f79f-00c04fc2dcd2
# Helper: extras\Grant-HashslingerReplicationRights.ps1 -GmsaName svc-hashslinger   (use -WhatIf first)

# On the scan server, elevated
Install-ADServiceAccount svc-hashslinger
Test-ADServiceAccount svc-hashslinger         # must print True

No other rights and no privileged group membership. The account also needs "Log on as a batch job" on the scan server if the task will not start.

How a scan works

StepWhat happens
1 PreflightOutput folder must be under an allowed report location; optional BitLocker check.
2 Merge wordlistsNew or changed files in data\staging are merged into the store (section Wordlists).
3 PatternsBuilds hashed candidates from pattern_rules.json (keyboard walks, base words, leetspeak, seasons, years, suffixes).
4 Pull from ADThe engine (Get-AccountHashes.ps1) runs an LDAP search for the scope (base DN, account types, UAC flags) to get the in-scope account GUIDs, then replicates them with DSInternals. bulk: one pass over the whole directory, keeping only in-scope accounts. per-account: one call per account. At or below per_account_threshold (5000) bulk switches to per-account automatically, since bulk costs the same for 2 accounts as for all. Explicit -Properties sets are used so no Schema partition rights are needed. Offline mode reads an ntds.dit copy instead. Hashes go to the exe over a pipe, never to disk.
5 MatchHashes are sorted, then looked up in the memory-mapped store (binary search plus a 2-byte prefix index). Pattern candidates, empty password, reversible encryption, LM hash, and (if on) duplicates are checked.
6 ReportWrites report_<date>.csv (flagged accounts only). Refuses to write any cell containing an account's hash.
7 WipeZeroes the in-memory hash and name buffers, deletes temp merge folders, writes the audit entry with wipe_confirmed, applies report retention.
  • One scan at a time (status\run.lock); a second start is refused and logged.
  • The scheduled task runs Hashslinger.exe --config ... scan as the service account on the cadence, day and time in settings.
  • Memory is about 150 to 250 bytes per account plus 40 for sorting.

Wordlists and the hash store

Drop files in data\staging\HIBP, rockyou or custom (copy, do not move, so they inherit the folder permissions). The store is a sorted file of 17-byte records: the 16-byte NT hash plus a 1-byte source tag (HIBP, rockyou, custom). Merging is a linear pass with an atomic swap; a scan never sees a half-written store.

FileHandled as
plain text (default for rockyou, custom)One password per line; NT hash computed.
.ntlm (default for HIBP)Lines of HASH or HASH:count.
.tsv / .csvHash column plus password column. Delimiter (tab, colon, comma), which column holds the hash, and an optional header are detected. The first rows are tested: if NT(password) equals the hash column it is used directly; otherwise the NT hash is computed from the password column and the hash column is ignored. Passwords are never stored. Single-column files are NT hash lists.
  • master.ntlm.manifest.json records each merged file by size and modified time. Only new or changed files are merged, all new files of one folder in a single pass, parsed in parallel.
  • The store is a union. Deleting a source file does not remove its hashes. To drop a list, rebuild (section Delete things).
  • Merge time is mostly disk speed; a full HIBP merge needs about twice the store size free. The source files are plaintext password lists; keep or delete them as you see fit.

Upgrade

Whole package

  1. Wait for any running scan to finish (or stop it). Setup refuses to run during a scan.
  2. Unzip the new package somewhere else (not inside the install folder). If it has no Hashslinger.exe, run build.cmd in it, or setup builds one with the in-box compiler.
  3. Run its Setup-Hashslinger.cmd, pick the same install folder (settings load automatically), click Install.

This backs up the current app\ to app-backups\app-<stamp> (last 3 kept), copies the new exe, scripts, docs and extras, and re-runs verification and Finish (tasks re-registered). Kept untouched: settings, store, wordlists, reports, logs, pattern_rules.json. New settings keys appear in the Admin tool with defaults; click Save to write them.

Single file

With no scan running, copy the new file over the old one in app\ (an exe or a script in app\powershell), then Unblock-File it. Nothing needs restarting. Config changes you can make in the Admin tool; pattern_rules.json can be edited in place.

Roll back

Copy the contents of app-backups\app-<stamp> back over app\. Settings: copy a config\hashslinger.json.bak-<stamp> over hashslinger.json.

Reinstall / move

  • Reinstall in place: same as the upgrade. Settings and data are kept.
  • Clean reinstall: uninstall with -RemoveAll (below), then run setup again. The store is rebuilt from the wordlists you supply.
  • Move to another drive or folder: uninstall tasks only (no switches), copy the whole install folder to the new location, run setup from the package and pick the new folder, then open the Admin tool and fix any path that still points at the old location (the Where tab). Copying data\store including the manifest avoids re-merging.
  • New server: create the service account for the new server name (or add the computer to the existing account's allowed list), run setup there.

Troubleshooting

SymptomCause / fix
Replication access was deniedOne of the two rights is missing, denied, or not on the domain root itself. The tool already passes explicit property sets so Schema rights are not needed. Run the service account checks; the effective-rights line and the live test say which.
"Only FIPS certified cryptographic algorithms ... MD5"FIPS-only .NET. DSInternals needs MD5 and RC4 for replication, so the scan is blocked (setup and permissions are fine). Needs a policy decision for this server or a different host. Check HKLM:\SYSTEM\CurrentControlSet\Control\Lsa\FipsAlgorithmPolicy Enabled=1.
0x80070534, "identity references could not be translated"The server cannot resolve the account through a DC: TCP 445 and 135, Test-ComputerSecureChannel.
Access denied on a wordlistFile kept its old permissions. Copy it in (do not move) or icacls <folder> /T /reset. Finish also repairs this.
Step 4 quiet for a long timeScope search then a bulk pull of the whole directory; progress lines show counts. Small scopes switch to per-account on their own.
Task will not startGrant the service account "Log on as a batch job".
Scripts blocked / ask to confirmStart from Setup-Hashslinger.cmd (it unblocks), or Get-ChildItem <folder> -Recurse | Unblock-File.
Search base not foundThe Users container is CN=Users, not an OU. Pick it from the tree.
Setup says a scan is runningWait, or Stop-Process -Name Hashslinger.
Need to send diagnosticsAdmin tool, Run and logs, Create support bundle (settings, logs, versions; no reports or hashes).
